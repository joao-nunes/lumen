# Personal Mental Health Tracking Assistant

## 1. Project Overview

A personal, multi-agent AI application designed to help users track, reflect on, and better understand their wellbeing over time.

The application combines conversational AI, structured self-reporting, longitudinal analytics, personal memory, and external research.

The system is intended for **personal use only**. It is **not intended for professional clinical use and does not replace qualified mental-health or medical support**.

The goal is not to diagnose or treat mental-health conditions. Instead, the application should help users:

* Track self-reported wellbeing over time.
* Reflect on their experiences, emotions, behaviours, and routines.
* Identify patterns and changes in their own data.
* Learn about mental-health and wellbeing topics using reliable sources.
* Maintain a longitudinal record of their reflections and check-ins.
* Build personal, non-clinical goals and routines.

---

# 2. Design Principles

The system should follow these principles:

### 2.1 Personal insight, not diagnosis

The system should describe and analyse user-provided information without presenting itself as a clinician or making unsupported diagnoses.

Prefer:

> "Your reported stress has increased over the last three weeks."

Over:

> "You are becoming clinically depressed."

### 2.2 Deterministic computation

Quantitative metrics, scores, trends, and statistical calculations should be computed by deterministic software rather than generated by an LLM.

LLMs may **interpret** computed results but should not invent them.

### 2.3 Evidence-based information

When providing general information about mental health, the Research Agent should prefer reliable sources such as scientific literature, healthcare institutions, and established public-health organizations.

### 2.4 User-controlled memory

The user should be able to understand what information is being stored and should have mechanisms to review and manage their personal data.

### 2.5 Explicit safety boundaries

Safety-sensitive conversations should follow predefined safety workflows rather than relying exclusively on free-form LLM behaviour.

### 2.6 Modular architecture

Agents should have narrowly defined responsibilities and communicate through explicit state rather than uncontrolled agent-to-agent conversations.

# 4. Agents

## 4.1 Greeter / Session Agent

### Responsibility

Manages the conversational entry point and session context.

Responsibilities include:

* Greeting the user.
* Starting and ending conversations.
* Explaining the application's capabilities.
* Initiating check-ins when appropriate.
* Passing user requests to the Orchestrator.

Authentication itself should be handled by the application authentication layer rather than an LLM.

---

## 4.2 Orchestrator Agent

### Responsibility

Determines what the user is trying to accomplish and routes the request to the appropriate workflow.

Possible intents include:

```text
CHECK_IN
REFLECTION
RESEARCH
HISTORY
ANALYTICS
PLANNING
GENERAL_CONVERSATION
SAFETY
```

The Orchestrator should not unnecessarily answer substantive questions itself.

It should primarily:

1. Understand the user's intent.
2. Determine required context.
3. Select the appropriate agent/workflow.
4. Pass structured state between components.
5. Return the final response to the user.

---

## 4.3 Check-in Agent

### Responsibility

Collects structured self-reported wellbeing information.

Potential dimensions:

* Mood
* Energy
* Stress
* Sleep quality
* Motivation
* Concentration
* Social connection

Each metric should use a clearly defined scale.

Initial scale:

```text
0–10
```

Example:

```text
Mood:             7/10
Energy:           5/10
Stress:           6/10
Sleep quality:   4/10
Motivation:       6/10
```

The Check-in Agent is responsible for conversational data collection and validation, not quantitative analysis.

---

## 4.4 Reflection Agent

### Responsibility

Helps users reflect on their experiences using their own historical data and journal entries.

The Reflection Agent may:

* Identify recurring themes.
* Summarize recent experiences.
* Ask reflective questions.
* Connect user-reported events with changes in wellbeing metrics.
* Explain quantitative trends in natural language.

It should distinguish between:

```text
OBSERVATION
DERIVED TREND
USER-REPORTED INFORMATION
INTERPRETATION
```

It should avoid presenting interpretations as clinical conclusions.

Example:

> "Your recorded stress has increased over the past three weeks, while your energy has decreased. You have also mentioned workload several times in your recent journal entries."

---

## 4.5 Research Agent

### Responsibility

Provides evidence-based information about mental health and wellbeing topics.

Example:

```text
User:
"What is burnout?"

        ↓

Orchestrator

        ↓

Research Agent

        ↓

Search / RAG

        ↓

Sources + retrieved information

        ↓

Research Agent

        ↓

User
```

The Research Agent should:

* Retrieve relevant information.
* Prefer authoritative sources.
* Provide citations where appropriate.
* Distinguish established evidence from uncertainty.
* Avoid diagnosing the user.

---

## 4.6 Safety Agent

### Responsibility

Handles safety-sensitive conversations.

The Safety system should detect potentially concerning content and route the conversation into predefined safety workflows.

The Safety Agent should not attempt to independently diagnose the user.

Safety logic should be implemented as a combination of:

```text
Deterministic rules
+
Model-based classification
+
Predefined response policies
```

rather than relying exclusively on free-form generation.

---

## 4.7 Planning / Coping Agent

### Status

Planned for a later version.

### Responsibility

Helps users create personal, non-clinical plans around goals and routines.

Examples:

* Sleep routines
* Exercise goals
* Journaling
* Work-life balance
* Personal routines
* Stress-management activities

The agent should not prescribe medical treatment.

---

# 5. Deterministic Services

Not every component should be an AI agent.

## 5.1 Authentication Service

Responsible for:

* User authentication.
* Session management.
* Authorization.
* Identity management.

LLMs should not authenticate users.

---

## 5.2 Memory Service

Responsible for persistent user information.

Potential storage:

```text
PostgreSQL
├── users
├── sessions
├── checkins
├── journal_entries
└── conversations
```

A vector database may be introduced later for semantic retrieval of journal entries.

---

## 5.3 Wellbeing Analytics

Responsible for deterministic quantitative analysis.

Potential calculations:

* Daily scores
* Weekly averages
* Rolling averages
* Change between periods
* Trends
* Variance
* Missing-data statistics
* Correlations between user-reported dimensions

Example:

```text
Mood
Week 1: 7.0
Week 2: 6.0
Week 3: 5.0
Week 4: 4.0

Trend: decreasing
```

The Analytics service produces the quantitative result.

The Reflection Agent interprets it conversationally.

---

# 6. Wellbeing Data Model

Initial dimensions:

| Dimension         | Scale | Meaning                          |
| ----------------- | ----: | -------------------------------- |
| Mood              |  0–10 | Self-reported mood               |
| Energy            |  0–10 | Perceived physical/mental energy |
| Stress            |  0–10 | Perceived stress                 |
| Sleep quality     |  0–10 | Subjective sleep quality         |
| Motivation        |  0–10 | Perceived motivation             |
| Concentration     |  0–10 | Ability to concentrate           |
| Social connection |  0–10 | Perceived social connection      |

These dimensions are **self-reported wellbeing indicators**, not clinical measurements.

---

# 7. Quantitative Analysis

The application should initially avoid producing a single "mental health score".

Instead, it should track multiple dimensions independently.

Example:

```text
Wellbeing

Mood             6.2  ↓
Energy           5.4  ↓
Stress           7.1  ↑
Sleep quality    4.8  →
Motivation       5.9  ↓
```

Possible derived metrics:

### Rolling average

$$
\bar{x}_{t,k}
=
\frac{1}{k}
\sum_{i=0}^{k-1} x_{t-i}
$$

### Period change

$$
\Delta =
\bar{x}_{current}
-
\bar{x}_{previous}
$$

### Trend

Estimate the slope of the metric over time.

The exact statistical methodology should be defined and tested before being exposed to users.

---

# 8. Memory

The system should distinguish between different types of memory.

### Structured memory

Examples:

```text
Check-in
Mood = 6
Stress = 7
Energy = 5
```

### Episodic memory

Examples:

```text
User mentioned feeling exhausted after work.
```

### Longitudinal summaries

Examples:

```text
User frequently reports increased stress during periods of
high workload.
```

The system should avoid turning speculative LLM interpretations into persistent facts.

# 11. Safety Architecture

Safety should be a graph-level concern rather than just another conversational capability.

Conceptually:

```text
START
  ↓
Safety Gate
  │
  ├── Safe ──────→ Orchestrator
  │
  └── Concerning → Safety Workflow
```

Safety-sensitive workflows should be explicitly defined, tested, and version controlled.

# 15. Current Priority

The immediate goal is **not** to implement all agents.

The first vertical slice should be:

```text
Check-in
    ↓
Structured data
    ↓
Persistence
    ↓
Analytics
    ↓
Trend visualization
```

Once this pipeline is reliable, the conversational agents can be progressively added around it.
