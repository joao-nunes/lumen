# Lumen — Personal Wellbeing Reflection Assistant

## 1. Project Overview

A personal, multi-agent AI application designed to help users track, reflect on, and better understand their wellbeing over time.

The application combines conversational AI, structured self-reporting, longitudinal analytics, personal memory, structured self-help exercises, and external research.

The system is intended for **personal use only**. It is **not intended for professional clinical use and does not replace qualified mental-health or medical support**. Where the user is in therapy, the system should **support** that therapy (e.g. by preparing for sessions), never compete with it.

The goal is not to diagnose or treat mental-health conditions. Instead, the application should help users:

* Track self-reported wellbeing over time.
* Reflect on their experiences, emotions, behaviours, and routines.
* Identify patterns and changes in their own data.
* Prepare for therapy sessions with a concise summary of the period since the last one.
* Run small, honest personal experiments on routines and habits.
* Work through structured, non-clinical self-help exercises.
* Learn about mental-health and wellbeing topics using reliable sources.
* Maintain a longitudinal record of their reflections and check-ins.

### 1.1 Engineering goals

Lumen is also a deliberate engineering-maturity and portfolio project. Some choices are intentionally more "production-grade" than a single-user tool strictly needs, in order to practise them properly:

* Multi-user support on PostgreSQL, with real authentication and per-user data isolation.
* A privacy layer that splits work between a local model and a hosted model.
* Deterministic, tested analytics.
* Explicit, version-controlled safety workflows.
* An evaluation suite built on synthetic data.
* Reproducible local deployment.

# 2. Design Principles

### 2.1 Personal insight, not diagnosis

The system should describe and analyse user-provided information without presenting itself as a clinician or making unsupported diagnoses.

Prefer:

> "Your reported stress has increased over the last three weeks."

Over:

> "You are becoming clinically depressed."

### 2.2 Deterministic computation

Quantitative metrics, scores, trends, experiment results, and statistical calculations should be computed by deterministic software rather than generated by an LLM.

LLMs may **interpret** computed results but should not invent them.

### 2.3 Evidence-based information

When providing general information about mental health, the Research Agent should prefer reliable sources such as scientific literature, healthcare institutions, and established public-health organizations.

### 2.4 User-controlled memory

The user should be able to understand what information is being stored and should have mechanisms to review and manage their personal data. Long-term memories are only persisted after explicit user approval (see §4.10).

### 2.5 Explicit safety boundaries

Safety-sensitive conversations should follow predefined safety workflows rather than relying exclusively on free-form LLM behaviour. Safety checks apply to both user input and agent output.

### 2.6 Modular architecture

Agents should have narrowly defined responsibilities and communicate through explicit state rather than uncontrolled agent-to-agent conversations.

A component is a separate agent only when its prompt, tools, or safety policy genuinely differ. Otherwise it should be a node, a function, or a deterministic service. Every additional LLM hop adds latency, cost, and a failure point.

### 2.7 Privacy by tiered processing

Raw personal text (journal entries, free-text check-ins, conversation transcripts) is processed by a **local model**. Hosted LLMs only receive redacted or pseudonymized content, or aggregated numbers (see §8).

### 2.8 Complement therapy, don't replace it

Features should point toward real-world support: preparing for therapy sessions, encouraging the user to bring topics to their therapist, and surfacing the user's own safety plan when needed.

### 2.9 Avoid rumination and dependence

Reflection should not become an endless loop over the same negative theme. After repeated turns on one theme, the system should gently steer toward a concrete action, a break, or noting the topic for therapy (see §4.3).

### 2.10 Low-friction tracking

Tracking only works if it is sustained. Check-ins should take under a minute, and the user should never be forced to fill in every field.

# 4. Agents

## 4.1 Orchestrator Agent

### Responsibility

Manages the session and determines what the user is trying to accomplish, then routes the request to the appropriate workflow.

Session responsibilities (formerly the Greeter agent):

* Greeting the user and starting/ending conversations.
* Explaining the application's capabilities.
* Suggesting a check-in when none has been recorded today.
* Surfacing pending items (e.g. memory candidates awaiting review, an unread weekly review, an upcoming therapy session).

Possible intents:

```text
CHECK_IN
REFLECTION
EXERCISE
THERAPY_PREP
WEEKLY_REVIEW
EXPERIMENT
RESEARCH
HISTORY
ANALYTICS
MEMORY_REVIEW
GENERAL_CONVERSATION
```

`SAFETY` is not an intent. It is handled by the Safety Gate before routing.

The Orchestrator should not unnecessarily answer substantive questions itself. It should:

1. Understand the user's intent.
2. Determine required context.
3. Select the appropriate agent/workflow.
4. Pass structured state between components.
5. Return the final response to the user.

---

## 4.2 Check-in Agent

### Responsibility

Collects structured self-reported wellbeing information with minimal friction.

### Check-in modes

1. **Structured.** The user fills in the core dimensions directly (UI form or conversational).
2. **Free text.** The user writes naturally, e.g. *"slept badly, stressful meeting, ok evening"*. The **local model** extracts candidate scores and tags. The agent shows them back and the user **confirms or corrects** them before anything is persisted.

### Dimensions

* **Core** (asked every check-in): mood, energy, stress.
* **Rotating** (asked on a schedule, e.g. a subset each day): sleep quality, motivation, concentration, social connection.

### Anchored scales

All dimensions use a **labelled 1–5 scale**. Every point has a user-visible anchor description, which reduces drift over time and makes check-ins faster than a 0–10 slider (see §6.1).

### Tags

Lightweight boolean/categorical context recorded with a check-in, e.g.:

```text
exercise, alcohol, caffeine_late, social_time, workday,
therapy_day, poor_sleep, conflict, time_outdoors
```

Tags are user-extensible and are a primary input to correlation analysis and personal experiments.

The Check-in Agent is responsible for collection and validation, not quantitative analysis.

---

## 4.3 Reflection Agent

### Responsibility

Helps users reflect on their experiences using their own historical data, journal entries, and approved memories.

The Reflection Agent may:

* Identify recurring themes.
* Summarize recent experiences.
* Ask reflective questions.
* Connect user-reported events with changes in wellbeing metrics.
* Explain quantitative trends in natural language.
* Suggest flagging a topic to bring up in therapy.

It should distinguish between:

```text
OBSERVATION
DERIVED TREND
USER-REPORTED INFORMATION
INTERPRETATION
```

It should avoid presenting interpretations as clinical conclusions.

### Rumination guard

A deterministic counter tracks consecutive turns on the same negative theme. Past a configurable threshold, the agent shifts from deeper exploration to one of:

* A concrete small action or structured exercise.
* Suggesting a pause.
* Flagging the topic for the next therapy session.

Example:

> "Your recorded stress has increased over the past three weeks, while your energy has decreased. You have also mentioned workload several times in your recent journal entries."

---

## 4.4 Research Agent

### Responsibility

Provides evidence-based information about mental health and wellbeing topics.

```text
User: "What is burnout?"
  ↓
Orchestrator
  ↓
Research Agent
  ↓
Search / RAG
  ↓
Sources + retrieved information
  ↓
Research Agent
  ↓
User
```

The Research Agent should:

* Retrieve relevant information.
* Prefer authoritative sources.
* Provide citations where appropriate.
* Distinguish established evidence from uncertainty.
* Avoid diagnosing the user.
* Send only generic queries to external search, never personal context (see §8).

---

## 4.5 Safety Agent / Safety Workflow

### Responsibility

Handles safety-sensitive conversations.

The Safety system should detect potentially concerning content and route the conversation into predefined safety workflows. It should not attempt to independently diagnose the user.

Safety logic should combine:

```text
Deterministic rules
+
Model-based classification (local model, so raw text stays on-device)
+
Predefined response policies
```

rather than relying exclusively on free-form generation.

### Input and output checks

* **Input gate:** classifies every user message before routing.
* **Output check:** screens every agent response before it reaches the user (e.g. no harmful content, no diagnostic claims, no dwelling on harmful details).

### Personal safety plan

Each user can author a safety plan based on the Stanley-Brown structure:

1. Personal warning signs.
2. Internal coping strategies.
3. People and places that provide distraction.
4. People to contact for help.
5. Professionals or services to contact (e.g. therapist, SNS 24, 112).
6. Making the environment safer.

When the safety workflow triggers, it presents the user's **own** plan alongside configured crisis resources, rather than generic text.

---

## 4.6 Therapy Prep Agent

### Responsibility

Helps the user arrive at therapy sessions prepared, and capture takeaways afterwards.

### Before a session

Generates a concise brief covering the period since the last recorded session:

* Wellbeing trends (from Analytics).
* Notable events and recurring journal themes.
* Topics the user explicitly flagged with "bring this up in therapy".
* Progress on active experiments or exercises.
* Open questions the user wants to ask.

The brief is editable by the user and exportable (Markdown/PDF).

### After a session

Prompts the user to record their own takeaways and any agreed actions. These notes are user-authored and stored as Tier 0 data (§8).

The agent does not interpret the therapist's work or offer competing advice.

---

## 4.7 Weekly Review Agent

### Responsibility

Produces a scheduled weekly review ("weekly letter") that builds a longitudinal narrative.

Triggered by the Scheduler (§5.5), not by the user. Contents:

* Weekly averages and changes per dimension (from Analytics).
* Notable tag correlations, with explicit sample-size caveats.
* Themes from the week's journal entries.
* Status of active experiments.
* One or two reflective questions for the coming week.
* Optionally, a short validated wellbeing questionnaire (WHO-5) every two weeks.

The review also produces **memory candidates** for the Memory Curator (§4.10). It never writes memories directly.

---

## 4.8 Personal Experiments Agent

### Responsibility

Helps the user design and run small n-of-1 experiments on routines and habits. This replaces the previously planned Planning/Coping Agent.

Example:

> "No caffeine after 14:00 for 14 days. Does my sleep quality improve?"

### Experiment lifecycle

```text
DRAFT → BASELINE → ACTIVE → COMPLETED / ABANDONED
```

Each experiment defines:

* Hypothesis (user's own words).
* Intervention (what changes).
* Outcome dimension(s) to watch.
* Baseline window and intervention window.
* Daily adherence tracking (did I stick to it today?).

### Analysis

Deterministic, performed by Analytics (§5.3):

* Mean difference between baseline and intervention windows.
* Uncertainty estimate (e.g. bootstrap confidence interval).
* Adherence rate and missing-data rate.
* Explicit warnings when sample sizes are too small to say anything.

The agent reports results honestly and never claims causation.

The agent should not prescribe medical treatment.

---

## 4.9 Structured Exercises Agent

### Responsibility

Guides the user step-by-step through structured, schema-defined self-help exercises. Each exercise is a fixed sequence of fields, and the agent's role is guidance and clarification, not free-form therapy.

Initial exercises:

### Thought record (CBT-style)

```text
Situation
Automatic thought
Emotion(s) + intensity (0–100)
Evidence for the thought
Evidence against the thought
Alternative / balanced thought
Emotion intensity after (0–100)
```

### Behavioural activation log

```text
Planned activity
Expected enjoyment / sense of achievement
Completed? (yes / no / partially)
Actual enjoyment / sense of achievement
```

Completed exercises are stored as structured records, can be referenced by Reflection and Therapy Prep, and can be exported.

---

## 4.10 Memory Curator

### Responsibility

Owns the boundary between transient observations and persistent long-term memory.

Other agents (Reflection, Weekly Review) can only **propose** memory candidates. The Curator:

1. Deduplicates and merges candidates.
2. Attaches provenance (source entries, check-ins, or conversations).
3. Labels each candidate with its type (`OBSERVATION`, `DERIVED_TREND`, `USER_REPORTED`, `INTERPRETATION`).
4. Presents candidates to the user for **approval, edit, or rejection**.

Only approved memories are retrieved by agents. Users can view, edit, and delete any stored memory at any time.

# 5. Deterministic Services

Not every component should be an AI agent.

## 5.1 Authentication Service

Multi-user by design, as an engineering exercise (§1.1). **Self-implemented** as a learning exercise, built on vetted cryptographic primitives. We write the auth flow ourselves but never write our own cryptography.

Responsible for:

* User registration and login.
* Password hashing with Argon2id (via `argon2-cffi`).
* Server-side sessions stored in PostgreSQL, referenced by an opaque random token in an `HttpOnly`, `Secure`, `SameSite` cookie. This is preferred over JWTs for a same-origin web app: sessions can be revoked and are easier to reason about.
* Session expiry, rotation on login, and logout or invalidation.
* CSRF protection for state-changing requests.
* Login rate limiting and generic error messages (no user enumeration).
* Authorization: every request is scoped to the authenticated user.
* Per-user data isolation, enforced in the database (PostgreSQL Row-Level Security) as well as the application layer.

The auth module must have its own security-focused test suite.

LLMs should not authenticate users.

---

## 5.2 Memory Service

Responsible for persistent user information, including retrieval for agents. It only returns **approved** long-term memories (§4.10).

Semantic retrieval over journal entries uses embeddings generated by the **local model** and stored in PostgreSQL via `pgvector`.

---

## 5.3 Wellbeing Analytics

Responsible for deterministic quantitative analysis.

Calculations:

* Daily scores
* Weekly averages
* Rolling averages
* Change between periods
* Trends
* Variance
* Missing-data statistics
* Correlations between dimensions
* Tag effects (e.g. mean stress on days with vs. without a tag)
* Experiment comparison (baseline vs. intervention, with uncertainty)
* Validated questionnaire scoring (e.g. WHO-5)

Example:

```text
Mood
Week 1: 4.0
Week 2: 3.6
Week 3: 3.1
Week 4: 2.7

Trend: decreasing
```

Analytics produces the quantitative result. Agents interpret it conversationally.

---

## 5.4 Privacy Layer

Responsible for keeping raw personal text on the user's machine. Runs a local model (e.g. via Ollama). Responsibilities:

* Extracting scores and tags from free-text check-ins.
* Generating embeddings for semantic retrieval.
* Safety classification of raw input.
* Redaction and pseudonymization of text before it is sent to a hosted model (see §8).
* Re-hydrating pseudonyms in hosted-model responses before they are shown to the user.

---

## 5.5 Scheduler

Responsible for time-based jobs:

* Weekly review generation.
* Biweekly questionnaire prompts.
* Experiment phase transitions (baseline → active → completed).
* Check-in reminders (in-app).

Because the application runs locally and may be offline, the scheduler must be idempotent and **catch up** on missed jobs at the next start.

# 6. Wellbeing Data Model

## 6.1 Dimensions

| Dimension         | Cadence  | Meaning                          |
| ----------------- | -------- | -------------------------------- |
| Mood              | Core     | Self-reported mood               |
| Energy            | Core     | Perceived physical/mental energy |
| Stress            | Core     | Perceived stress                 |
| Sleep quality     | Rotating | Subjective sleep quality         |
| Motivation        | Rotating | Perceived motivation             |
| Concentration     | Rotating | Ability to concentrate           |
| Social connection | Rotating | Perceived social connection      |

These dimensions are **self-reported wellbeing indicators**, not clinical measurements.

### Scale

Every dimension uses a labelled 1–5 scale, with one anchor description per point. Anchors are defined per dimension. A higher value is not always "better": higher stress means more stress. The direction of each dimension must therefore be explicit in the model so that Analytics and the UI can say "better" or "worse" correctly.

Example (mood, wording to be refined):

| Value | Label     | Anchor                                         |
| ----: | --------- | ---------------------------------------------- |
|     1 | Very low  | Struggling to feel anything positive           |
|     2 | Low       | Mostly down, with brief better moments         |
|     3 | Neutral   | Neither good nor bad                           |
|     4 | Good      | Generally positive                             |
|     5 | Very good | Clearly positive, light, engaged               |

# 7. Quantitative Analysis

The application should avoid producing a single "mental health score".

Instead, it should track multiple dimensions independently.

```text
Wellbeing

Mood             3.2  ↓
Energy           2.9  ↓
Stress           3.8  ↑
Sleep quality    2.6  →
Motivation       3.1  ↓
```

### Rolling average

$$
\bar{x}_{t,k}
=
\frac{1}{k}
\sum_{i=0}^{k-1} x_{t-i}
$$

### Two questions, two windows

| Question                  | Method                                   | Default window                 |
| ------------------------- | ---------------------------------------- | ------------------------------ |
| "How am I doing lately?"  | Period change Δ                          | Last 28 days vs. previous 28   |
| "Where am I heading?"     | Trend slope                              | Last 12 weeks                  |

Wellbeing changes slowly relative to day-to-day noise, so a slope needs a long window to be distinguishable from noise. A difference between two period means is detectable with less data.

### Autocorrelation

Day-to-day wellbeing is "sticky": a bad day tends to be followed by another. Treating days as independent overstates the information in the data and gives intervals that are too narrow. Every interval therefore uses an effective sample size (Santer et al., 2000):

$$
n_{eff} = n \, \frac{1 - \rho_1}{1 + \rho_1}
$$

where $\rho_1$ is the lag-1 autocorrelation, bias-corrected for short series as $\rho_1 \approx (n r_1 + 1)/(n - 3)$ (Kendall; Marriott & Pope) and clamped at 0. Consecutive observations are treated as adjacent even across missing days. If $n_{eff} < 4$, no interval is reported.

### Period change

$$
\Delta =
\bar{x}_{current}
-
\bar{x}_{previous}
$$

reported with a 95% Welch-style confidence interval, where each period's variance of the mean and Welch–Satterthwaite degrees of freedom use its own $n_{eff}$.

### Trend

Ordinary least-squares slope of daily values against day number (only days with data), reported per week with a 95% confidence interval. The standard error and degrees of freedom use $n_{eff}$ computed from the residuals.

### Classification

The same rule applies to slopes and to changes:

| Direction             | Rule                                                   |
| --------------------- | ------------------------------------------------------ |
| Increasing/decreasing | CI excludes 0 **and** \|estimate\| ≥ threshold         |
| Flat                  | CI lies entirely within ±threshold                     |
| Unclear               | Otherwise: the data cannot separate signal from noise  |
| Insufficient data     | Too few points, or $n_{eff} < 4$                       |

Practical thresholds (provisional): 0.1 points/week for trends, 0.25 points for period change.

Direction is combined with each dimension's polarity to give an outlook (improving / worsening / stable / unknown).

### Calibration

Interval coverage is verified by simulation (`tests/analytics/test_calibration.py`) on data rounded to the 1–5 scale, with skipped days and lag-1 autocorrelation of 0–0.5: 95% intervals achieve ≥ 91% coverage in the test, and ~94–96% in larger runs. For very sticky data (autocorrelation ≈ 0.7) coverage drops to ~89–93%, a known limitation.

With 7 dimensions, roughly 1 in 20 comparisons of unchanging data will still be flagged by chance. Consumers (Weekly Review, Reflection) should treat a single flagged change as tentative.

### Experiment effect

$$
\hat{\delta} = \bar{x}_{intervention} - \bar{x}_{baseline}
$$

reported with a bootstrap confidence interval, adherence rate, and a minimum-sample-size guard.

The exact statistical methodology should be defined and tested before being exposed to users. All analytics outputs must state the number of data points they are based on.

# 8. Privacy Model

Privacy uses a tiered approach: raw text stays local, and hosted models see only redacted or aggregated data.

| Tier | Data                                                                                                  | May leave the machine?                             |
| ---- | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| 0    | Raw journal text, free-text check-ins, transcripts, therapy notes, safety plan, names of people        | **Never**                                          |
| 1    | Redacted/pseudonymized excerpts and summaries produced by the local model                             | Yes, to the hosted LLM                             |
| 2    | Aggregated numeric analytics, generic research queries                                                | Yes                                                |

### Pseudonymization flow

```text
Raw text (Tier 0)
  ↓  local model: detect names, places, employers, other identifiers
Pseudonymized text ("[PERSON_1] criticised my work at [ORG_1]")   (Tier 1)
  ↓  hosted LLM
Response with pseudonyms
  ↓  local re-hydration (pseudonym map never leaves the machine)
User
```

### Additional rules

* A **local-only mode** setting disables all hosted-model calls (degraded quality, full privacy).
* Every hosted-model call is logged locally (what tier was sent, by which agent) so the user can audit it.
* Redaction is best-effort. Its quality is part of the evaluation suite (§13).

# 9. Memory

The system distinguishes between different types of memory.

### Structured memory

```text
Check-in
Mood = 3
Stress = 4
Energy = 3
```

### Episodic memory

```text
User mentioned feeling exhausted after work.
```

### Longitudinal summaries

```text
User frequently reports increased stress during periods of
high workload.
```

Longitudinal summaries and other long-term memories go through the Memory Curator (§4.10) and require user approval. The system must not turn speculative LLM interpretations into persistent facts.

# 12. Safety Architecture

Safety is a graph-level concern rather than just another conversational capability.

```text
START
  ↓
Input Safety Gate (rules + local classifier)
  │
  ├── Safe ──────→ Orchestrator → Agent → Output Safety Check → User
  │
  └── Concerning → Safety Workflow → User's safety plan + crisis resources
```

Safety-sensitive workflows should be explicitly defined, tested, and version controlled. Any validated questionnaire containing a self-harm item must route positive responses into the safety workflow.

# 13. Evaluation

### Synthetic personas

Create 2–3 synthetic users with ~90 days of generated data each, e.g.:

* **Gradual burnout:** rising stress, falling energy, workload themes.
* **Stable:** noisy but flat metrics.
* **Seasonal dip:** a slow decline followed by recovery.

These serve as fixtures for unit tests, analytics validation, and agent evaluation without using real personal data.

### Evaluate

* Intent classification and routing accuracy
* Free-text check-in extraction accuracy
* Analytics correctness
* Experiment analysis correctness (including small-sample guards)
* Redaction/pseudonymization recall
* Retrieval quality
* Reflection quality and rumination-guard behaviour
* Memory candidate quality (precision of proposed memories)
* Safety detection (input and output)
* Response quality

* Define domain models and wellbeing dimensions.
* PostgreSQL schema with migrations (Alembic).
* Multi-user auth and Row-Level Security.
* Implement Analytics.
* Synthetic personas.
* Unit tests.

### Milestone 2 — Check-in vertical slice

* Structured check-in (core + rotating dimensions, tags).
* Local web app shell.
* Persistence → Analytics → trend visualization.

### Milestone 3 — Privacy layer

* Local model integration.
* Free-text check-in extraction with confirmation.
* Embeddings + pgvector.
* Redaction / pseudonymization and re-hydration.
* Hosted-call audit log.

### Milestone 4 — Orchestration and safety

* LangGraph workflow and intent routing.
* Input safety gate and output safety check.
* Safety plan authoring and safety workflow.
* Safety evaluation dataset.

### Milestone 5 — Reflection and memory

* Journal entries.
* Reflection Agent with rumination guard.
* Memory Curator and approval UI.

### Milestone 6 — Weekly review and therapy prep

* Scheduler with catch-up.
* Weekly Review Agent (+ WHO-5).
* Therapy sessions, flags, and Therapy Prep Agent with export.

### Milestone 7 — Exercises and experiments

* Thought record and behavioural activation.
* Personal Experiments Agent and experiment analytics.

### Milestone 8 — Research

* Research Agent, retrieval, and source attribution.

### Milestone 9 — Hardening

* Full evaluation suite.
* User settings, local-only mode.
* Export/delete functionality.
* Docker Compose deployment.

# 16. Current Priority

The immediate goal is **not** to implement all agents.

The first vertical slice is:

```text
Check-in
    ↓
Structured data
    ↓
Persistence (multi-user PostgreSQL)
    ↓
Analytics
    ↓
Trend visualization (local web app)
```

Once this pipeline is reliable, the privacy layer and conversational agents can be progressively added around it.

# 17. Decisions

| Decision           | Choice                                                                   |
| ------------------ | ------------------------------------------------------------------------ |
| Users              | Multi-user (engineering practice), personal use                          |
| Database           | PostgreSQL (+ pgvector for embeddings)                                   |
| Privacy            | Tiered: local model for raw text, hosted LLM for redacted/aggregated data |
| Interface          | Local web app on desktop: FastAPI backend + React/TypeScript frontend    |
| Wellbeing scale    | Labelled 1–5 with per-dimension anchors                                  |
| Authentication     | Self-implemented (Argon2id, server-side sessions, RLS)                   |
| Greeter agent      | Merged into Orchestrator                                                 |
| Safety             | Input gate + output check + user-authored safety plan                    |
| Planning agent     | Replaced by Personal Experiments Agent                                   |
| New features       | Therapy Prep, Weekly Review, Experiments, Structured Exercises, Memory Curator |
| Wearables          | Out of scope                                                             |

# 18. Open Design Questions

* Anchor wording for each dimension.
* Rotation schedule for non-core dimensions.
* Which validated questionnaires to support beyond WHO-5.
* Experiment methodology.
* Practical thresholds (0.1/week, 0.25 points) and default windows, to validate against real use.
* Handling multiple comparisons across dimensions (e.g. requiring persistence across weeks before flagging).
* Hosted LLM provider/model.
* Local model choice (extraction, redaction, safety classification) and embedding model.
* Frontend tooling details (build tool, component library, charting library).
* Application-level encryption and key management.
* LangGraph state schema.
* Safety taxonomy and policies.
* Scheduler implementation (in-process vs. separate worker).
* Data retention policy.
* Evaluation methodology and metrics thresholds.
